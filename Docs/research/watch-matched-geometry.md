## What Apple actually guarantees

Apple's watchOS article puts a `TabView` inside `NavigationStack`, uses `.verticalPage`, and matches a first-page image with a leading toolbar image. Its two `isSource` conditions are complementary. The article says the animation follows the Digital Crown. It adds no custom animation modifier. That is direct support for the original feature design. [Apple's watchOS 10 UI article](https://developer.apple.com/documentation/watchos-apps/creating-an-intuitive-and-effective-ui-in-watchos-10)

The general API contract says `matchedGeometryEffect` copies selected geometry from the currently inserted source. Exactly one inserted member of a group must have `isSource == true`; otherwise behavior is undefined. Matching does not control rendering or transitions. A persistent renderer with `isSource: false` and two clear source placeholders therefore uses the documented geometry relationship, provided exactly one source exists at runtime. [matchedGeometryEffect](https://developer.apple.com/documentation/swiftui/view/matchedgeometryeffect(id:in:properties:anchor:issource:))

The coordinate distinction matters here. `.frame` combines `.position`, measured in window coordinates, with `.size`, measured in local coordinates. The `anchor` parameter selects a relative point in the view; it does not select a different coordinate space. A named coordinate space on the root cannot change MGE's window-position contract. [MatchedGeometryProperties](https://developer.apple.com/documentation/swiftui/matchedgeometryproperties), [matchedGeometryEffect parameters](https://developer.apple.com/documentation/swiftui/view/matchedgeometryeffect(id:in:properties:anchor:issource:))

`geometryGroup` changes where SwiftUI resolves geometry. Normally it pushes ancestor size and position changes down to drawing leaves. A group resolves and animates those changes at the parent, then passes the result to children. Apple describes a barrier, not a cache of endpoint rectangles or protection against every ancestor transition. Placing it on different sides of MGE changes which subtree the barrier encloses. [geometryGroup](https://developer.apple.com/documentation/swiftui/view/geometrygroup())

A transaction carries the context of one state update. Its root animation comes from the changed binding and any `withAnimation` or `withTransaction` context. It is discarded after the update. `isContinuous` describes an action producing repeated values; Apple gives slider dragging and holding a stepper as examples. It is not a documented Digital Crown progress API. [Transaction](https://developer.apple.com/documentation/swiftui/transaction), [isContinuous](https://developer.apple.com/documentation/swiftui/transaction/iscontinuous)

Apple explains that `.animation(_:value:)` writes an animation when the supplied value changes. An unconditional transaction override applies on every update reaching that modifier and can produce unwanted descendant animations. SwiftUI also provides closure-scoped animation and transaction modifiers to affect only the modifiers inside the closure. This explains why the session's selection-scoped and unconditional overrides need separate testing. It does not explain the exact size jump by itself. [Explore SwiftUI animation, transaction chapter](https://developer.apple.com/videos/play/wwdc2023/10156/?time=1200)

## Ranked candidates

This section records the earlier investigation and rejected probes. Its ranking predates the final high-confidence-only requirement. It does not authorize further variants, and the current app retains native transition timing.

### 1. Resolve both endpoint anchors into one stable outer source proxy

This is the strongest remaining architectural experiment. Keep native vertical pagination and the persistent graph. Have the page placeholder and the toolbar placeholder publish independent `.bounds` anchor preferences, without MGE. Resolve both anchors using one `GeometryProxy` belonging to a stable outer overlay. Place one persistent clear source proxy and the graph renderer in that overlay. Derive the source proxy's frame and position from the anchor for the selected tab. The proxy always has `isSource: true`; the renderer always has `isSource: false`. The original placeholders provide layout and hit testing.

Apple documents anchors as opaque geometry associated with a view. `GeometryProxy` converts them into the target container's coordinate space. Preferences carry anchors up the view tree. This supports using measured rectangles without fixed screen offsets. It does not guarantee continuous presentation geometry during a native tab transition. [Anchor](https://developer.apple.com/documentation/swiftui/anchor), [Anchor.Source](https://developer.apple.com/documentation/swiftui/anchor/source), [GeometryProxy](https://developer.apple.com/documentation/swiftui/geometryproxy)

Prediction: if MGE's participants inherit incompatible native parent transforms, moving the source and renderer under one parent should remove the position snap. Keeping the source flag constant also removes the handoff as a possible trigger. If the resolved endpoint rectangles themselves jump, the experiment will expose that jump rather than hide it. Prefer `overlayPreferenceValue` resolution to copying every geometry update into `@State`. Keep both identities stable and enforce exactly one source, including when an endpoint preference is absent. Hide the graph until a valid measurement exists; later, preserve the last valid rectangle or use a defined valid fallback. Do not silently remove the only source or substitute a zero rectangle.

The architecture is an implementation inference, and the measured-origin variant now has partial positive runtime evidence described below. It is not Apple's published recipe for vertical pages.

Check feasibility before implementing the proxies. Publish the toolbar and page anchors, then confirm that both reach the outer overlay at rest and during paging. No primary source found here promises that a custom preference emitted by hosted `ToolbarItem` content reaches an overlay outside `NavigationStack`. The documented anchor conversion applies to an anchor available to the target container. It does not establish cross-host preference delivery. Apple's preference overview describes values flowing from subviews toward their container, which reconciles them. If the toolbar preference is missing, this recipe needs a different measurement route. [Preferences](https://developer.apple.com/documentation/swiftui/preferences), [anchorPreference](https://developer.apple.com/documentation/swiftui/view/anchorpreference(key:value:transform:))

The publish-only probe received both keys 0 and 1 at the root initially. It resolved the graph rectangle as x 13, y 27, width 178, height 95 points, and the toolbar rectangle as x 13, y -35, width 35, height 35 points. During paging, graph key 0 disappeared on the macro page, toolbar key 1 remained, and graph key 0 returned on reversal at x 13, y -22.8992, width 178, height 95 points. This establishes delivery and also shows that the measured graph endpoint can include native page translation.

The first common-root source proxy trial matched the resting layout, but failed during motion. It enlarged offscreen, crossed the clock, then snapped from clipped y 0 to y 32 as width changed from 356 to 355 pixels. The same-parent arrangement and constant source flag therefore are insufficient when the proxy follows raw moving-page geometry.

The normalization probe adds a full-page bounds anchor under key 2 after a frame with infinite maximum width and height. The root resolves graph key 0 and page key 2 through the same proxy. Native pagination remains in place, and the toolbar target comes from its measured 35-point bounds.

The first normalization run showed the mini ring at initial rest because the ancestor's `.anchorPreference` wrote only page key 2 and replaced the descendant graph key 0. This was a preference-wiring error, not evidence against canonical motion. The parent changed it to `.transformAnchorPreference`, mutating the existing dictionary with `anchors[2] = pageAnchor`. Apple documents that overload as combining the preference key's current value with the current view's anchored geometry. [transformAnchorPreference](https://developer.apple.com/documentation/swiftui/view/transformanchorpreference(key:value:transform:))

The next centering attempt failed its resting-layout gate. Root reader size was 204 by 159 points, but the page rectangle was x 0, y 9, width 204, height 150. The graph relative to that page was x 13, y 18, width 178, height 95. The root reader therefore did not describe the actual page viewport. Treating their origins as interchangeable or deriving a centering correction from root size was incorrect. This is a measured layout mismatch, not a canonical-motion verdict.

The current candidate caches the first valid resting page origin in root coordinates, initially x 0, y 9, with page size 204 by 150 points. It computes `canonicalMain.origin = rawMain.origin - currentPage.origin + cachedRestPageOrigin`, preserving main size. At that initial rest the two page origins cancel, so the result reproduces the measured raw main rectangle. During later page translation it removes the current page displacement while retaining the original page placement. The overlay also caches the last valid main and toolbar rectangles separately to handle absent preferences.

Resting layout passed. The main ring remained x 30, y 77, width 356 pixels; the mini ring remained x 34, y 36, width 70 pixels. In a quick Crown pair, reversal showed y 36, 39, 44, 50, then movement toward 77 as the ring grew. The former 28-pixel reverse position jump was absent, and the ring did not clip or cross the clock. This is a partial positive result on the tested build, not a full fix verdict.

One forward run held width 344 pixels in repeated frames 59 through 62, sampled at 20 ms, then showed width 276 in frame 63 over 8.33 ms. Later testing passed a 3-second forward touch and a 2.5-second reverse touch. Held cancellation returned to main correctly. A completed held reverse retarget showed raster width 344 to 276 pixels over 11.67 ms, then 276 to 233. A fast return showed width 81 to 155 over 3.33 ms. Position followed size without a separate 28-pixel step, and no duplicate ring appeared.

The remaining width observations need classification. They establish large differences between sampled raster bounds; they do not establish a mathematical discontinuity in the underlying animated property. The simulator's incremental Crown chains, using offsets 0.03 and waits 0.15, did not reliably accumulate selection and could time out. Those chains do not provide a valid slow Crown verdict.

The plain Circle renderer-isolation probe kept the same cached common-root source, endpoint measurements, and animation topology. It added `.frame(maxWidth: .infinity, maxHeight: .infinity)` before the Circle's geometry group and MGE so its proposal matched the graph's `GeometryReader`. At rest, the Circle and real graph shared center x 208, y 255 pixels. Their diameters were 190 and 356 pixels respectively because the Circle fits the shorter matched dimension.

During slow forward touch, the Circle width changed from 185 to 156 pixels. The 29-pixel step is 24.2 percent of its 120-pixel endpoint size range. The real graph's earlier 68-pixel step is 23.8 percent of its 286-pixel range. The first distinct Circle rasters were 13.333 ms apart; adjacent samples were 10 ms apart. Position tracked width without a separate 28-pixel snap. This reproduction rules out custom ring drawing as necessary for the remaining size step. Similar normalized step sizes do not establish the exact cause or remove the capture-timing caveats.

Subtracting the page origin removes translation only. It does not invert scale, rotation, or an arbitrary native transform. Verify that the page and graph sizes remain stable before treating the relative rectangle as a canonical endpoint. Recompute it only when both anchors exist. Preserve the last valid main-relative rectangle when key 0 is absent rather than substituting toolbar geometry for a selected main target.

Separate endpoint caches preserve the selected endpoint when only the other endpoint currently publishes a measurement. The quick Crown pair provides evidence for the combined arrangement, but does not isolate the contribution of caching from page-origin normalization.

The origin cache depends on its first valid page measurement representing rest. The current app starts on tab 0, and the session expects that measurement before page interaction. Apple does not promise that the first preference delivery is a settled frame. Anchor conversion also does not give a cached point automatic validity after root size, safe-area, or toolbar layout changes. Invalidate or recapture the reference if those inputs change, using a settled layout rather than copying a mid-transition origin. The current fixed-layout probe does not establish a general cache invalidation policy.

The earlier forced-timing probe used two steady endpoint targets and a timed smooth animation. That inspected source applied `.animation(.smooth(duration: 0.3), value: graphFrame)` to both the source proxy and renderer, so any unequal measured rectangle can activate that modifier, even if selection stays unchanged. Native fractional gesture coupling is not established by this design. Held touch and retarget tests passed the position checks but showed the size observations recorded above; slow incremental Crown behavior remains unverified.

The whole-overlay trial adds one unconditional smooth transaction to the outer ZStack while retaining the existing child `.animation(_:value: graphFrame)` modifiers. Its first calibrated Circle run had a slow largest sampled step of 18 of 120 pixels, or 15 percent, versus the prior 29 of 120, or 24.2 percent. Held retarget's largest sampled step was 21 of 120, or 17.5 percent, versus the prior 44 of 120, or 36.7 percent. The trial's first distinct held rasters changed from width 125 to 104 over 15 ms; the prior comparison changed from 179 to 135 over 31.667 ms. Neither showed an independent position rebase or duplicate ring. Different start widths and timestamp gaps make this a preliminary one-run improvement, not causal proof.

In that earlier probe, the parent restored the real graph with the unconditional outer smooth transaction retained. The graph applies `.animation(.bouncy(duration: 0.6), value: mode)` before geometry group and MGE to preserve mode changes. The origin capture now observes the first valid main/page pair through `onChange(of: mainFrame == nil ? nil : pageFrame)`, and all temporary debug logs were removed. This avoids relying only on page changes when the main measurement arrives later.

That real candidate passed two exact 3-second forward and 2.5-second reverse touch pairs. Original resting positions remained correct. Neither showed the old roughly half-range source-size jump or the independent 28-pixel position step. The largest recorded forward change was width 314 to 269, or 45 of the 286-pixel size range, 15.7 percent, over 16.666 ms since the last distinct raster. The first reverse's largest change was 112 to 155, or 43 of 286, 15 percent, over 16.667 ms. Other recorded largest changes were 38 and 36 pixels.

Those frame changes could occur near an ordinary velocity peak of a 0.3-second spring. A threshold based only on an absolute 40-pixel change is not an adequate discontinuity test: it ignores size range, elapsed time, velocity, and missing intermediate rasters. This is a positive repeated slow-touch result, not proof of a fully fixed implementation.

Later real-graph held cancellation and retargeting, plus individual Crown input in both directions, reached the correct pages. They showed neither the original roughly half-range source-size snap nor an independent 28-pixel origin snap. Held retarget's largest recorded change was 45 of 286 pixels, 15.7 percent. Crown reverse changed width 82 to 148, or 66 of 286, 23.1 percent, about 15 ms after the first 82-pixel raster. Fast return changed 81 to 155, or 74 of 286, 25.9 percent, over 16.666 ms since the first 81-pixel raster. Position followed the size path without a separate rebase, and no duplicate ring appeared.

The unconditional smooth transaction improved the tested slow-touch and some held samples. It did not eliminate all larger sampled size steps. A capture or rendering gap and an MGE timeline issue remain possible explanations; neither is established. The result was a partial improvement before the user rejected its timing. The current app source has the real graph and no Circle prototype or debug logs. Simulator taps in both the center and outer graph area changed mode correctly and restored the corresponding ring and label. The parent reports that the user's catalog, project, and icon hashes remained unchanged. An initial physical installation attempt failed, but a later attempt installed and launched the revised native-timing version, as recorded below.

The earlier failed unconditional override on only the renderer used native endpoints with changing source flags, so it does not establish the result for the current single stable source in a common root. Rectangle-noise rounding remains a diagnostic proposal if noise is first measured.

Keep the proxy's endpoint-sized frame immediately inside MGE and its explicit root-local position outside MGE. This ordering is an implementation inference intended to match the measured child rather than a positioning wrapper. Apple documents `frame` as a fixed-size enclosing view and `position` as setting the child's center in its parent's coordinate space. [frame](https://developer.apple.com/documentation/swiftui/view/frame(width:height:alignment:)), [position](https://developer.apple.com/documentation/swiftui/view/position(x:y:))

Negative toolbar coordinates are valid when the root container starts below the toolbar; do not clamp them. The parent plans to place the toolbar preference before its existing 2-point offset so that it measures the intended child rectangle. Verify the resulting resting visible ring against the baseline, since preference attachment order changes which view supplies the bounds.

### 2. Full-size outer host that ignores the container safe area, rejected

The session tested a stable full-size overlay host with explicit top-leading alignment and `.ignoresSafeArea(.container, edges: .all)`. Both existing anchor overrides and the renderer's selection-scoped animation remained in place.

The expected resting ring retained x 30, y 77, and width 356 pixels. Crown reversal still moved the 70-pixel ring from x 34, y 36 to x 34, y 8 in 11.667 ms. This was a negative result. Do not retain this host change as a fix.

Apple says ignoring safe areas expands the size proposal. It also warns that fixed-size content can align unexpectedly and that ignored edges influence alignment. `.container` includes device and container UI such as top and bottom bars. This API changes the proposal and alignment basis; it does not promise to freeze geometry. [ignoresSafeArea](https://developer.apple.com/documentation/swiftui/view/ignoressafearea(_:edges:)), [SafeAreaRegions.container](https://developer.apple.com/documentation/swiftui/safearearegions/container)

The probe predicted that changing the proposed container basis might change or remove the snap. It did neither. This lowers the priority of further safe-area tuning; it does not establish which internal native transform is responsible.

```swift
            id: "calorieGraph",
            in: calorieGraphNamespace,
            properties: .frame,
            isSource: isGraphSource
        )
    }
```

Apple explicitly limits the mutation to modifiers inside `body`. This differs from replacing or mutating the transaction for the entire descendant subtree. [transaction(_:body:)](https://developer.apple.com/documentation/swiftui/view/transaction(_:body:))

The probe predicted that isolating the override might preserve the width fix while avoiding an animation side effect in the descendant subtree. The same position snap remained. This lowers the priority of further transaction-scope variants, but does not prove that every transaction arrangement has identical behavior.

## Remaining width steps and interruption semantics

Apple documents `.smooth` as a spring without bounce. Its spring documentation describes successive spring animations replacing one another while preserving velocity. Apple's spring session also describes continuous position and velocity when a moving animation is retargeted. This supports checking interruption continuity. It does not prove that MGE's internal geometry bookkeeping, cache updates, or a captured video has those properties. [smooth](https://developer.apple.com/documentation/swiftui/animation/smooth), [spring](https://developer.apple.com/documentation/swiftui/animation/spring), [Animate with springs](https://developer.apple.com/videos/play/wwdc2023/10158/?time=1117)

`.animation(_:value:)` monitors an `Equatable` value and applies its animation when that value changes. A truly equal `graphFrame` therefore does not freshly activate this modifier. `CGRect` equality compares rectangle origin and size; Apple documents no approximate-equality tolerance for this comparison. An unconditional transaction mutation is different because it can write an animation during updates where the monitored rectangle remains equal. [animation(_:value:)](https://developer.apple.com/documentation/swiftui/view/animation(_:value:)), [CGRectEqualToRect](https://developer.apple.com/documentation/coregraphics/cgrectequaltorect(_:_:))

The broad transaction changes mode-animation behavior unless the graph restores it locally. `toggleMode` supplies `.bouncy(duration: 0.6)` through `withAnimation`; the unconditional outer override replaces that inherited animation inside the overlay even when `graphFrame` remains equal. The children monitoring `graphFrame` do not restore an animation for an unchanged trigger. That forced-timing real graph restored the mode animation before geometry group and MGE, and simulator mode checks passed. The current native-timing graph retains the local mode animation without the outer override. This follows the documented transaction flow; the earlier version had no measured mode regression. [Transaction](https://developer.apple.com/documentation/swiftui/transaction), [transaction(_:body:)](https://developer.apple.com/documentation/swiftui/view/transaction(_:body:))

One falsifiable hypothesis is small rectangle noise. Subtracting two converted anchor origins may produce tiny unequal results while the intended normalized target is constant. The earlier forced-timing modifiers monitored the entire rectangle, so unequal targets could activate another explicit animation transaction. Those modifiers are now removed. In the current source, rectangle changes can still update layout, but this explicit-retarget explanation no longer applies. Log full-precision x, y, width, and height, the equality comparison with the previous target, selection, and which anchor keys exist. If the target is exactly unchanged through a width step, this hypothesis fails. If only origin changes, the logs still do not prove a width retarget. The claim that repeated updates restart `.smooth` from rest would conflict with the documented spring expectation unless another animation or implementation behavior is involved.

Quantizing measured targets is a diagnostic only after nonzero noise is observed. It should suppress noise smaller than a rendered pixel without altering the resting endpoints or swallowing real layout changes. Rounding a rectangle before any noise measurement would hide evidence and could create its own discrete target steps.

Another hypothesis is a geometry-to-state update problem. Anchor preferences send values toward their container; this overlay then stores endpoint fallbacks in state. Apple warns against using `onChange` to bounce data back and forth without a need, and against geometry changes invalidating large view trees. The current external overlay does not automatically form a cycle: a cycle requires its stored values to change the upstream geometry being measured. Log whether fallback-cache writes alter the active `graphFrame`, especially when graph key 0 disappears or returns. A cache value changing while it is unused is different from an active endpoint switching to a different fallback. No such cycle has been established. [Preferences](https://developer.apple.com/documentation/swiftui/preferences), [SwiftUI Group Lab, common anti-patterns](https://developer.apple.com/videos/play/wwdc2026/8006/?time=619), [onGeometryChange](https://developer.apple.com/documentation/swiftui/view/ongeometrychange(for:of:action:))

`geometryGroup` resolves parent geometry before passing it to children. A persistent source does not change that contract. A group may keep the ring leaves under one transform; it does not promise continuous measurements, stable caches, or timely rendering. The width steps do not establish a group-placement defect or justify another ordering change under the current high-confidence-only requirement. [geometryGroup](https://developer.apple.com/documentation/swiftui/view/geometrygroup())

For variable-frame-rate captures, compare each distinct raster with its actual presentation timestamp and the elapsed time since the last distinct raster. Repeated images followed by a large change could represent duplicated capture samples, dropped rendered updates, or an animation target change. A short interval after the final repeated image is not enough to distinguish them. Record both the repeated-frame span and the final interval, and align target logs using monotonic uptime. A stable target with missing intermediate images supports a rendering or capture gap; a changed target at that point supports retargeting, but still needs continuity evidence. These are measurement inferences, not an Apple diagnosis.
