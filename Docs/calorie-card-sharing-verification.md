Implementation branch: `codex/calorie-card-sharing`. Local tickets live under `.scratch/calorie-card-sharing/issues/`. The [specification](calorie-card-sharing-spec.md) defines product behavior; [research](research/calorie-card-sharing-cloudkit.md) records API and policy evidence.

## Implementation

The native calorie card and received card share one explicit presentation. An immutable snapshot stores recorded totals and a coherent Now/Midnight pair, the sender's date and time zone, portable colors, unit, and only a visible goal result. A recipient never supplies calorie preferences or recomputes a projection.

A separate SQLiteData database stores account-scoped connections, cached snapshots and durable work. A separate minimal alert table records verified account identifiers, proposal identifiers and expiry only. Atomic claims prevent repeated automatic request alerts across restarts and account switches; expired identifiers are pruned. It does not synchronize the existing day-choice database, HealthKit samples or Settings. The coordinator exposes consent actions and filtered snapshots to the UI. The same interface accepts either the real CloudKit adapter or the deterministic two-person fake.

The direct CloudKit adapter owns the sharing synchronization lane. SQLiteData 1.12.0 remains the local database. Its public sharing interface does not provide the independent read-only-share departure operation, and its automatic row synchronization does not expose the same-zone publisher-authority compare-and-swap that this protocol needs. The dedicated adapter therefore performs explicit private/shared reads and atomic encrypted record writes, plus share creation, acceptance, departure and revocation. It does not replace the app's other persistence.

Each connection has a metadata-only writable discovery hierarchy. Its URLs are untrusted. Each account separately owns a read-only control hierarchy; the adapter verifies the CloudKit share owner, account, container and connection before reading consent events. Events from writable discovery records never authorize calorie disclosure. Today and History have separate outgoing hierarchies in each account. Publication waits for accepted scopes and verified reciprocal setup. Received cards are read-only.

On confirmed account changes the store erases received cards, sender calendars and publication authority. Only minimal account-bound reduction/removal work and directional receipts survive, so a later return can finish removing access without restoring old calorie payloads.

The phone identifier uses a nonsynchronizing Keychain item with `AfterFirstUnlockThisDeviceOnly` accessibility. A restored backup on another phone cannot inherit the publishing phone identifier from UserDefaults. Publisher authority lives in the owner's private zone. A publication saves its publisher record, scope root and complete snapshot together using atomic `ifServerRecordUnchanged` writes. A takeover changes the publishing generation. Cleanup reads the current publisher record's sender timezone and atomically compares that authority record with each deletion batch. Nonpublisher devices cannot run cleanup. Publication attempts independent dates and connections after ordinary failures, retains the first error, and stops on authority loss. Even an empty successful-read batch retries durable cleanup. Publisher control metadata propagation is fenced by the same authority record and repaired after interrupted setup. Reductions durably record outgoing share deletion and incoming share departure separately. Local viewing and publication stop before either server operation finishes. Old consent generations cannot authorize newly created scope hierarchies.

CloudKit database subscriptions request quiet background opportunities. HealthKit observer queries watch active, resting and dietary energy on supported hardware. Foreground refresh and normal successful dashboard refreshes also publish and fetch. A root-scene task prunes permitted dates even while person detail is open, waking at known sender midnight or request expiry with a minute cap for clock changes. Background delivery remains best effort. Failed reads and uploads preserve the previous successful cloud card and capture time.

### Corrections found by live testing

CloudKit represents the authenticated participant as `__defaultOwner__` in `CKShare.currentUserParticipant`. Verification now accepts that alias only for the current participant and retains owner, container, role and permission checks. CloudKit also rejected deleting a parent and its children together. Outgoing revocation now removes the share, then children, then root, and repairs cleanup when the share is already absent.

The normal typed-email Invite flow revealed a gap in the known-account-ID tests. A valid email participant can have no user record ID until metadata acceptance. The adapter now saves the exact email participant ID and original proposal in the inviter's encrypted private directory. Only the inviter's private CKShare can bind the exact accepted participant to a verified account. That binding creates the original consent proposal idempotently. System metadata acceptance grants no calories. Explicit in-app consent and reciprocal readiness remain required. The decision is recorded in [ADR 0001](adr/0001-bind-email-invitations-after-cloudkit-acceptance.md).

Pending invitations remain visible with Send and Cancel after the creation sheet closes. A real UI regression test exposed a List row whose name tap triggered cancellation. The final v16 buttons isolate their actions. Tapping the name preserves the invitation, Send opens the native share sheet, and only Cancel removes it. Their measured touch height is 50.3 points.
